# Hamara Tunnel and 3x-ui Integration

> Compatibility target: **3x-ui v3.8.0**, the upstream release published on 2026-09-14. Verify the upstream release page before production upgrades because 3x-ui changes quickly.
>
> Official project: https://github.com/MHSanaei/3x-ui
Release page: https://github.com/MHSanaei/3x-ui/releases/tag/v3.8.0

This document explains how to integrate 3x-ui with an already working Hamara Tunnel. It does not configure WireGuard inside 3x-ui; WireGuard belongs to the operating system.

## Recommended order

1. Install Hamara Tunnel on the two VPSs.
2. Confirm `sudo wg show` reports a recent handshake.
3. Confirm tunnel IP connectivity, for example `ping 10.77.0.1` from the client side.
4. Confirm the desired route with `ip route get <destination>`.
5. Install or configure 3x-ui.
6. Create the Xray inbound and outbound.
7. Test through the tunnel, then tighten firewall rules.

## Install and connect 3x-ui

The simplest topology is to run 3x-ui/Xray on the foreign VPS and use Hamara only as the private transport:

```text
Iran VPS (Hamara client) === WireGuard === Foreign VPS (Hamara server + 3x-ui/Xray)
```

Install 3x-ui from its upstream installer, then complete the first-login hardening:

```bash
bash <(curl -Ls https://raw.githubusercontent.com/MHSanaei/3x-ui/master/install.sh)
sudo x-ui
```

Use the panel's generated URL and credentials. Immediately change the random/default panel settings, restrict the panel management port to your administrator IP or a private interface, and enable TLS for panel access where appropriate. Do not treat the panel port as your tunnel port.

In the panel, create an **Inbound** under the current `Inbounds` page. Select the protocol and transport required by your authorized application, set its listen address and port, create a client, save it, and use the generated link or QR code on the client application. The panel can manage protocols including VLESS, VMess, Trojan, Shadowsocks and other Xray-supported inbounds; exact form labels can vary by v3.8.x build.

To make the inbound reachable through Hamara, first confirm that Xray listens on the intended address:

```bash
ss -lntup
ip addr show wg0
```

- For a service used only between the two VPSs, bind it to the foreign tunnel address such as `10.77.0.1`.
- For a public inbound, bind it to the foreign public address or `0.0.0.0` and open only the required provider and host firewall port.
- Do not bind the panel itself to a public address unless necessary.

On the Iran VPS, clients do **not** connect to the WireGuard interface as if it were an Xray subscription. They connect using the Xray client link/QR generated by 3x-ui. The operating system then routes the selected traffic over Hamara according to `AllowedIPs` and the route table.

If 3x-ui is installed on the Iran VPS instead, reverse the application placement: keep the Xray service bound to the Iran host, and use GOST or WireGuard port forwarding only for the specific service ports that must reach the foreign VPS. Do not enable two competing default routes.

## Foreign-side exit

If the foreign VPS is the egress host, ensure:

```bash
sysctl net.ipv4.ip_forward
ip route show default
iptables -t nat -S POSTROUTING
```

The foreign host must have a default route, forwarding enabled, and masquerading for the tunnel subnet if private client addresses need internet access.

## Binding and routing

The 3x-ui panel manages Xray. The OS manages WireGuard. Depending on your Xray build and panel version:

- Bind a service to the foreign tunnel address when it must be reachable over the tunnel.
- Use Xray routing rules for destination-specific selection.
- Use the OS route table for simple interface-wide routing.
- Avoid sending the WireGuard endpoint itself through the tunnel.

Start with a narrow `AllowedIPs` list instead of `0.0.0.0/0`. Add only the networks required by the application.

## Example checks

```bash
ss -lntup
sudo wg show
ip addr show wg0
ip route
sudo journalctl -u wg-quick@wg0 --no-pager
```

Test the Xray service locally before testing from a remote client. If the service is listening only on `127.0.0.1`, it will not be reachable through the tunnel address.

## Troubleshooting

### Xray works locally but not through the tunnel

Check the listener bind address, tunnel route, firewall input policy, and whether the service is actually listening on `10.77.0.1` or `0.0.0.0`.

### Xray connects but has no internet access

Check the foreign VPS forwarding and NAT rules independently of 3x-ui. Use `curl` from the foreign host and inspect transfer counters in `wg show`.

### Full route creates a loop

Keep the WireGuard endpoint reachable through the WAN table. Use split routes during initial setup and add explicit endpoint routes when multiple default routes exist.

### Panel changes are lost

Do not edit Xray generated files blindly. Make changes through 3x-ui, and keep the Hamara network configuration under `/etc/wireguard/`.

## Security

Use strong panel credentials, update 3x-ui and Xray, restrict management ports, and do not expose the panel to the public internet unless necessary. This guide assumes you are authorized to operate the VPSs and the services.
